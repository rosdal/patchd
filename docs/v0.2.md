# Patchd v0.2 — Linux Scan Dev Todo

Oct 14, 2026 · @Mark

v0.2 is done when `patchd scan` lists the installed packages and the pending updates on Debian, Ubuntu, Proxmox VE and Raspberry Pi OS, and its count matches apt's own on every homelab node. It is **read-only**: it never takes the dpkg lock and never changes the system, so it is safe to run anywhere from day one. Builds on the v0.1 skeleton.

## 1. Decisions to make first

These four choices shape every file in v0.2, so record each one as an ADR before writing code (section 11).

| Decision | Choice | Why |
| --- | --- | --- |
| Sync or async providers | **Async** trait via `async-trait`, on tokio (`rt`, `macros`, `process`, `time`) | The v0.3 agent is a long-running scheduler with timeouts and cancellation; changing later means touching every provider. Plain async fns in traits aren't usable through `dyn Provider`, hence the crate |
| Which apt command | `apt-get` and `dpkg-query`, **never `apt`** | `apt` prints "does not have a stable CLI interface", and its output changes between versions. `apt-get` and `dpkg-query` are the scriptable interfaces |
| upgrade or dist-upgrade simulation | `apt-get -s dist-upgrade` | Proxmox VE explicitly requires `dist-upgrade`/`full-upgrade`. A plain `upgrade` keeps back packages that need new dependencies, so the scan would undercount |
| Where the report schema lives | Rust types are the source; `schemars` generates `protocol/schemas/scan-report.json`, and CI fails if the schema drifts | The agent produces this data, so Rust-first is natural. `openapi.yaml` references the generated schema. Server-owned endpoints stay OpenAPI-first |

**The scan in order.** `patchd scan` runs these steps:

1. Detect the host and OS.
2. Ask each provider whether it applies here (`detect`).
3. Each applicable provider lists what is installed (`inventory`) and what can be updated (`available`). Every command goes through one command runner.
4. Assemble a `ScanReport`.
5. Render it as a table or JSON and exit with a meaningful code.

```rust
#[derive(Debug, Clone, Serialize, Deserialize, JsonSchema)]
pub struct Package {
    pub provider: ProviderId,          // "apt"

#[serde(rename_all = "snake_case")]

#[derive(Debug, Clone, Serialize, Deserialize, JsonSchema)]

    pub provider: ProviderId,
    pub name: String,
    pub arch: Option<String>,
    pub from_version: Option<String>,  // None = new dependency

    pub kind: UpdateKind,
    pub origins: Vec<String>,          // "Ubuntu:24.04/noble-security"

}

#[derive(Debug, Clone, Serialize, Deserialize, JsonSchema)]
pub struct ScanReport {
    pub schema_version: u32,           // 1
    pub agent_version: String,         // from build::LONG_VERSION
    pub scanned_at: jiff::Timestamp,
    pub host: HostInfo,
    pub providers: Vec<ProviderReport>,
}

#[derive(Debug, Clone, Serialize, Deserialize, JsonSchema)]
pub struct ProviderReport {
    pub id: ProviderId,
    pub packages: Vec<Package>,
    pub updates: Vec<Update>,
    pub removals: Vec<String>,         // packages dist-upgrade would remove
    pub index_age_secs: Option<u64>,   // how stale the package lists are
    pub warnings: Vec<String>,
    pub error: Option<String>,         // provider failed; others still report
}
```

- [ ] Make `ProviderId` a newtype around `&'static str`/`String` with constants (`ProviderId::APT`); serialize it as a plain string
- [ ] `provider.rs`:

```rust
#[async_trait]
pub trait Provider: Send + Sync {
    fn id(&self) -> ProviderId;
    async fn detect(&self, host: &HostInfo) -> bool;
    async fn inventory(&self) -> Result<Vec<Package>, ProviderError>;
    async fn available(&self) -> Result<Available, ProviderError>;   // updates + removals + age + warnings
}
```

- [ ] `ProviderError` (thiserror) with variants `Command(RunError)`, `Parse { line: usize, msg: String }` and `Unsupported(String)`. A parse error carries the line number, so a bug report can point at the exact apt output that broke
- [ ] `UpdateKind` rule for apt:
  - **Security** when any origin is a security suite.
  - **Major** when the upstream major version changes, e.g. `2.x` to `3.x` (rare inside a stable release, but it happens with backports).
  - **Minor** otherwise.
- [ ] Write unit tests for the `UpdateKind` rule

## 3. Debian version comparison

You need a correct Debian version comparison now (for `UpdateKind`) and again later: verifying an apply in v0.3, and showing "fixed in" in v0.8. It is about 100 lines, but it is easy to get subtly wrong, so test it against `dpkg` itself.

- [ ] `version::DebVersion::parse(&str)`:
  - The epoch is everything before the **first** `:` (default 0).
  - The revision is everything after the **last** `-` (absent revision = empty, which compares equal to `0`).
  - The upstream version is the part in between.
- [ ] `impl Ord for DebVersion`:
  - Compare epochs numerically, then upstream versions, then revisions.
  - Each string is compared as alternating non-digit and digit runs. Non-digit runs compare character by character with dpkg's order: `~` sorts before everything (even end of string), then end of string, then letters, then other characters.
  - Digit runs compare numerically, with leading zeros ignored.
- [ ] `upstream_major()` helper (first numeric run of the upstream version) for the Major rule
- [ ] Write table tests, each one checked by hand with `dpkg --compare-versions A lt B`:

| A | B | Expected |
| --- | --- | --- |
| `1.0~rc1` | `1.0` | A < B |
| `1.0~~` | `1.0~` | A < B |
| `1.0` | `1.0a` | A < B |
| `1.0` | `1.0+b1` | A < B |
| `2.30-2` | `2.30-2ubuntu1` | A < B |
| `1.0-1` | `1.0-10` | A < B |
| `1:0.1` | `2.0` | A > B |
| `1.01` | `1.1` | A = B |

- [ ] Cross-check test, ignored unless `dpkg` is present: take every version pair from the fixtures (section 10), compare each with your implementation and with `dpkg --compare-versions`, and assert they agree. It runs in the Linux test job (see section 10)
- [ ] Optional: a `proptest` that `parse(v.to_string()) == v` and that ordering is transitive

## 4. Command runner

Every external command goes through one trait. That gives the same locale, timeouts and logging everywhere, and it lets tests swap in recorded output, so providers are tested without a real Debian system.

- [ ] `runner.rs`:

```rust
pub struct Cmd {
    pub program: &'static str,         // "dpkg-query"
    pub args: Vec<String>,
    pub timeout: Duration,
}

pub struct CmdOutput { pub status: i32, pub stdout: String, pub stderr: String }

#[async_trait]
pub trait Runner: Send + Sync {
    async fn run(&self, cmd: &Cmd) -> Result<CmdOutput, RunError>;
}

#[derive(Debug, thiserror::Error)]
pub enum RunError {
    #[error("{0} not found")] NotFound(&'static str),
    #[error("{program} timed out after {secs}s")] Timeout { program: &'static str, secs: u64 },
    #[error("{program} exited {code}: {stderr}")] Failed { program: &'static str, code: i32, stderr: String },
    #[error(transparent)] Io(#[from] std::io::Error),
}
```

- [ ] `SystemRunner` on `tokio::process::Command`:
  - Clear the locale: `LC_ALL=C`, `LANG=C`, and remove `LANGUAGE`, so apt's output is always English and parseable.
  - Use `kill_on_drop(true)` and wrap the call in `tokio::time::timeout`.
  - Capture stdout and stderr; decode them with `String::from_utf8_lossy`, since package descriptions may not be valid UTF-8.
- [ ] Keep "exited non-zero" separate from "ran fine". `run` returns `Failed` only when the caller hasn't marked that exit code as expected (add an `ok_codes: &[i32]` field to `Cmd`)
- [ ] Add a `tracing` span per command (program, args, duration, exit code). Keep stdout at `trace` level only, because it can be megabytes
- [ ] Default timeouts: 30 s for `dpkg-query`, 120 s for `apt-get -s`. Configurable later in v0.3
- [ ] `FixtureRunner` for tests: maps `program + args` to a recorded `CmdOutput` loaded from `tests/fixtures/`, and panics on an unexpected command, so tests also prove you run only what you mean to
- [ ] Unit tests: timeout fires (run `sleep 5` with a 100 ms timeout), missing binary gives `NotFound`, and the locale is applied (run `env` and check for `LC_ALL=C`)

## 5. Host and OS detection

Host detection reads files directly instead of running commands: that is faster, and it works in minimal containers that lack `lsb_release` or `hostnamectl`.

- [ ] `HostInfo { hostname, os: OsInfo, arch, kernel }` and `OsInfo { id, id_like: Vec<String>, version_id, codename, pretty_name }`
- [ ] os-release parser:
  - Read `/etc/os-release`, falling back to `/usr/lib/os-release` (the systemd spec order).
  - Lines are `KEY=value`. Values may be double- or single-quoted, with backslash escapes inside double quotes. Skip comments and blank lines.
- [ ] Unit tests with real os-release files checked in under `tests/fixtures/os-release/`:
  - Ubuntu 22.04, 24.04, 26.04
  - Debian 12, 13
  - Raspberry Pi OS (64-bit)
  - a Proxmox VE host, which reports plain Debian; note that in a test name so nobody "fixes" it
- [ ] Hostname via the `gethostname` crate, which also works on Windows in v0.4
- [ ] Kernel from `/proc/sys/kernel/osrelease`; `arch` from `std::env::consts::ARCH`. The binaries are native per target, so this is the machine's architecture too
- [ ] Detect when Patchd runs inside a container (`/.dockerenv` or `container=` in `/proc/1/environ`), and add a warning to the report. Patching inside a container is almost never what someone wants

## 6. apt provider: inventory

`dpkg-query` with an explicit tab-separated format is stable across all supported releases, and it is fast (well under a second for \~1,500 packages).

- [ ] `AptProvider::detect`: `dpkg-query` and `apt-get` both exist on `PATH`. Check the binaries, not os-release, so derivatives (Mint, Pop!\_OS, Proxmox) work without a list
- [ ] Command:

```bash
dpkg-query -W -f='${binary:Package}\t${Version}\t${Architecture}\t${db:Status-Abbrev}\n'
```

- [ ] Parse each line into 4 fields:
  - `${binary:Package}` includes the `:arch` suffix for multi-arch packages (`libc6:i386`). Keep it as the name, so amd64 and i386 copies stay distinct.
  - `${db:Status-Abbrev}` is 3 characters: desired / status / error. Keep a package only when the 2nd character is `i` (installed).
  - The 1st character `h` means held, so set `held = true`.
  - Skip `rc` (removed, config left) packages; they are not installed.
- [ ] Add a warning when any package has an error flag (3rd character not a space), or a half-installed state (`iU`, `iF`, `iH`). This flags broken dpkg state before v0.3 tries to apply on top of it
- [ ] Fixture tests: a captured `dpkg-query` output per distro, asserting the package count and a few known packages (`base-files`, `libc6`)

## 7. apt provider: available updates

All update detection comes from one dry run, `apt-get -s dist-upgrade`, which works without root and without taking the dpkg lock. Its `Inst` lines carry the old version, the new version and every origin, which is all you need to classify security updates.

- [ ] Command: `apt-get -s -q dist-upgrade`. As non-root, apt adds a "NOTE: This is only a simulation!" line, so ignore any line that doesn't start with `Inst`, `Remv` or `Conf`
- [ ] Parse `Inst` lines with one regex and a fixture test per form:

```text
Inst libssl3t64 [3.0.13-0ubuntu3.4] (3.0.13-0ubuntu3.5 Ubuntu:24.04/noble-updates, Ubuntu:24.04/noble-security [amd64])
Inst base-files [12.4+deb12u7] (12.4+deb12u8 Debian:12.8/stable [amd64])
Inst libgnutls30 [3.7.9-2+deb12u3] (3.7.9-2+deb12u4 Debian-Security:12/stable-security [arm64])
Inst linux-image-6.8.0-49-generic (6.8.0-49.49 Ubuntu:24.04/noble-updates [amd64])
```

- [ ] Field rules:
  - `[old]` present means an upgrade (`from_version = Some(old)`).
  - `[old]` absent means a **new dependency**, typically a new kernel package (`from_version = None`). This is why the scan uses dist-upgrade.
  - Origins are comma-separated `Label:Version/Suite`. The trailing `[arch]` belongs to the whole line.
- [ ] `Remv <pkg> [<ver>]` lines go into `removals`. A dist-upgrade that wants to remove packages is worth a loud warning, because on Proxmox it can mean a broken repo setup
- [ ] Security rule: any origin whose suite ends in `-security` (`noble-security`, `stable-security`, `bookworm-security`), or whose label is `Debian-Security`. Ubuntu often lists a fix under both `-updates` and `-security`; it still counts as security
- [ ] Held packages: dist-upgrade skips them silently.
  - Run `apt-mark showhold`.
  - Run `apt-cache policy <held…>` and compare `Installed:` with `Candidate:`.
  - Report each held package that has a newer candidate as an `Update` with `held: true`. Without this, the count will never match `apt list --upgradable`.
- [ ] Ubuntu **phased updates**: dist-upgrade holds back packages whose rollout phase hasn't reached this machine. In v0.2, add a warning on Ubuntu hosts and allow for the difference in the exit check. Revisit in v0.3, when apply has to respect phasing anyway
- [ ] Index age: the newest mtime of `/var/lib/apt/lists/*_Packages` gives `index_age_secs`. Add a warning when it is older than 24 h, since the scan is only as fresh as the last `apt-get update`
- [ ] `--refresh` flag: runs `apt-get update -q` first. It requires root; without root, fail with a clear message rather than a partial scan. This is the only write v0.2 does, and it touches only package lists
- [ ] Fixtures per distro: `apt-get -s dist-upgrade` with at least one security update, one regular update, one new dependency, and one host with a held package

## 8. CLI: `patchd scan`

Give the CLI a human table by default, stable JSON for scripts, and exit codes that monitoring can use directly, for example a Home Assistant command sensor or a cron mail.

- [ ] Switch to clap subcommands: `patchd scan [--json] [--quiet] [--provider apt] [--refresh] [--packages]`
- [ ] Logging: `tracing-subscriber` to **stderr**, controlled by `-v`/`-vv` and `RUST_LOG`. stdout stays clean for `--json | jq`
- [ ] Default table output via `comfy-table` (pick one table crate and stick with it). Show only updates; `--packages` adds the full inventory:

```text
host  pve-elitedesk · Debian GNU/Linux 12 (bookworm) · x86_64 · lists 3h old

KIND      PACKAGE        FROM              TO                ORIGIN
```

- [ ] `--json`: the full `ScanReport`, pretty-printed, one object, no extra output on stdout

| Code | Meaning |
| --- | --- |
| 0 | Scan OK, nothing to update |
| 10 | Updates available, none security |

## 9. Protocol: ScanReport schema

The JSON that `patchd scan --json` prints today is exactly what the agent will POST to `/agent/inventory` in v0.6. Pinning its schema now means the server can be built against a contract rather than against whatever the agent happens to emit.

- [ ] Small `xtask` crate (`cargo xtask schema`) that writes `schemars::schema_for!(ScanReport)` to `protocol/schemas/scan-report.json`
- [ ] In `protocol/openapi.yaml`: `components.schemas.ScanReport: { $ref: "./schemas/scan-report.json" }`, so the OpenAPI lint job checks it too
- [ ] CI step: run `cargo xtask schema`, then `git diff --exit-code protocol/`, failing with "run cargo xtask schema" when the schema drifts
- [ ] Compatibility rule in `docs/protocol.md`: inside one `schema_version`, only **add** optional fields. Renaming or removing a field means `schema_version: 2`
- [ ] A test that validates the golden JSON from section 8 against the generated schema, with the `jsonschema` crate as a dev-dependency

## 10. Tests

The testing has three layers. Parsers are tested against recorded output on every commit; snapshot tests catch accidental changes to the report; and a container job runs the real binary against real apt on five distros.

**Fixtures**

- [ ] Layout: `crates/patchd-core/tests/fixtures/apt/<distro>/` holding `os-release`, `dpkg-query.txt`, `apt-get-s-dist-upgrade.txt`, and optionally `apt-mark-showhold.txt` and `apt-cache-policy.txt`
- [ ] `scripts/capture-fixtures.sh <image|ssh-host> <name>`: runs the exact commands from sections 6–7 with `LC_ALL=C` and writes the files above
- [ ] Capture from containers: `ubuntu:22.04`, `ubuntu:24.04`, `ubuntu:26.04`, `debian:12`, `debian:13`. Debian 13 and newer Ubuntu ship apt 3.x, so these fixtures are what prove the parser survives the apt 3 changes
- [ ] Capture from real hosts: both Proxmox nodes and the Pi. Replace the hostname with `example` before committing
- [ ] Container images are often fully up to date, leaving nothing to test. For edge cases, add small hand-written fixtures: a held package, a `Remv` line, a new kernel dependency, an epoch version (`1:2.3-4`), and multi-arch `:i386`

**Snapshots**

- [ ] Add `insta` (with its `json` feature) as a dev-dependency, plus `cargo install cargo-insta`. Snapshot the parsed `ProviderReport` per fixture with `insta::assert_json_snapshot!`, redacting `scanned_at`
- [ ] Commit `.snap` files; any parser change shows up as a reviewable snapshot diff (`cargo insta review`)

**Container integration job** (added to `ci.yml`)

```yaml
  scan-integration:
    needs: test
    runs-on: ubuntu-latest
    strategy:
      fail-fast: false
      matrix:
        image: ["ubuntu:22.04", "ubuntu:24.04", "ubuntu:26.04", "debian:12", "debian:13"]
    container: ${{ matrix.image }}
    defaults:
      run:
        shell: bash
    steps:
      - uses: actions/checkout@v4
      - uses: actions/download-artifact@v4
        with:
          name: patchd-x86_64-unknown-linux-musl
          path: bin
      - run: chmod +x bin/patchd
      - run: apt-get update -q && apt-get install -y -q jq
      - name: Scan
        run: |
          set +e
          bin/patchd scan --json > report.json
          code=$?
          [ "$code" -eq 0 ] || [ "$code" -ge 10 ]
      - name: Compare with apt
        run: |
          ours=$(jq '[.providers[] | select(.id=="apt") | .updates[] | select(.from_version != null and (.held | not))] | length' report.json)
          theirs=$(apt-get -s -q dist-upgrade | grep -cE '^Inst [^ ]+ \[' || true)
          echo "patchd=$ours apt=$theirs"
          [ "$ours" -eq "$theirs" ]
```

- [ ] Add `scan-integration` jobs to the required status checks in the `main` ruleset
- [ ] The `dpkg --compare-versions` cross-check from section 3 runs in the normal `test` job on `ubuntu-latest`, which has `dpkg`. Make it skip, not fail, where `dpkg` is missing (Windows, macOS)

## 12. Release v0.2.0 and exit check

Release the same way as v0.1: bump the version on a branch, merge the PR, tag `main`. Then check on real machines with the release binary, not a local build.

- [ ] Branch `release/v0.2.0`: `cargo release version minor --execute`, then `git cliff --tag v0.2.0 -o CHANGELOG.md`, then a PR and merge
- [ ] `git tag -a v0.2.0 -m "v0.2.0" && git push origin v0.2.0`; check that the release has 3 archives, `SHA256SUMS` and attestations
- [ ] On **each Proxmox node** and the **Pi**, run `sudo apt-get update`, then compare:

```bash
# upgrades patchd sees (excluding new dependencies)
patchd scan --json | jq '[.providers[0].updates[] | select(.from_version != null)] | length'

# what apt calls upgradable (includes held packages)
apt list --upgradable 2>/dev/null | tail -n +2 | wc -l
```

- [ ] The two numbers are **equal** on Debian, Proxmox and Raspberry Pi OS. On Ubuntu, a difference is allowed only for phased updates, which `patchd` reports as a warning
- [ ] Every update `apt list --upgradable` shows as `-security` is `kind: security` in `patchd scan`
- [ ] `patchd scan --quiet; echo $?` prints `11` when security updates are pending and `0` right after a full upgrade
- [ ] `patchd scan` as a **non-root** user works, and `sudo patchd scan --refresh` refreshes the index age to about 0
- [ ] Running it never changes `dpkg -l` output or `/var/lib/dpkg/lock-frontend` (`stat` before and after) — read-only proven
- [ ] Roadmap: tick off v0.2
