## Goal and definition of done

This TODO takes Patchd from v0.3 (Patchd IR) to v0.4, **milestone M1**: the first real vulnerability findings. Taint analysis inside single functions finds command injection, path traversal and SQL injection, and `patchd scan` reports them as SARIF with a step-by-step trace. Estimated: 4–6 weeks for one engineer.

**Done means all of these are true:**

- [x] `patchd scan <path>` finds every in-scope known issue (Step 9) in NodeGoat and DVNA: the command-injection, path-traversal and SQL-injection bugs whose source and sink sit in the same function.
- [x] Zero findings on the safe fixture suite (100+ cases) and on Patchd's own TypeScript code.
- [x] Every finding has a CWE, severity, message, trace and stable fingerprint.
- [x] SARIF output validates against the SARIF 2.1.0 schema and uploads cleanly to GitHub code scanning. *(Validated in tests; uploaded by the `patchd-scan` job on #23, which code scanning accepted as the "Patchd" check.)*
- [x] Analysis adds under 30 seconds on top of load and lowering for a 500k-line repo.
- [x] Tag `v0.4.0` exists. *(On 08c0df6, the merge of #23.)*

**Out of scope for v0.4:** flows across functions or files (v0.5), YAML models and other frameworks (v0.6), any other rule. If a source and sink are in different functions, v0.4 misses it, by design.

## Step 0 · Taint design ADR and test targets

**`docs/adr/0010-taint-model.md`**

- [x] **Taint kinds**, not a single "tainted" bit: `user-input` (origin) plus the sink-specific kinds it can become (`sql`, `command`, `path`, `url`, `html`, `code`). A sanitizer clears specific kinds only (`encodeURIComponent` clears `url`, not `sql`).
- [x] **Lattice**: each value maps to a set of taint labels; join is set union; bottom is the empty set. Labels carry the origin (source location) so traces can be reconstructed.
- [x] **Sound where cheap, precise where it matters**: unknown calls propagate taint from arguments to the result by default (conservative), but never invent taint from nothing.
- [x] **Field sensitivity**: none in v0.4 (an object is tainted as a whole); planned for v0.5. Record this as a known source of false positives.
- [x] **Reporting rule**: a finding needs a concrete path from a source to a sink argument with a matching kind and no clearing sanitizer on the path.
- [ ] ADR reviewed and accepted before Step 1. *(Written before Step 1, amended during triage, marked Accepted in Step 12; no human review yet: review it with the PR.)*

**Test targets (analysed, never run)**

- [x] Add OWASP NodeGoat, DVNA and OWASP Juice Shop to `eval/targets/reference-repos.yaml` (pinned commits) if not already there; `pnpm targets:fetch` installs with lifecycle scripts disabled.

## Step 1 · Dataflow framework

A small, generic framework that taint and every later analysis reuse.

- [x] `engine/dataflow/lattice.go`: a `Lattice[T]` interface: `Bottom()`, `Join(a, b)`, `Leq(a, b)`.
- [x] `engine/dataflow/solver.go`: forward worklist solver over a `Func`'s blocks in reverse post-order; transfer function per instruction; iterates to a fixed point; respects exceptional edges.
- [x] Because the IR is SSA, most facts attach to values, not program points: implement a **sparse** solver that propagates along def-use chains, with a dense per-block fallback for memory (`load`/`store` on cells and globals).
- [x] `engine/dataflow/defuse.go`: def-use chains built once per function and cached.
- [x] `engine/dataflow/reaching.go`: reaching stores for cells and module globals inside a function (needed so `store cell = tainted; …; load cell` propagates).
- [x] Widening and an iteration cap per function (default 50 passes) with a warning when hit; never loop forever.
- [x] Unit tests on hand-built IR: straight line, branches, loops, try/catch, captured cells. *(Small TypeScript snippets lowered by `ir.BuildModule`: the IR's argument slices are unexported, so it can't be built by hand outside `engine/ir`.)*
- [x] Commit: `feat(engine): dataflow framework`.

## Step 2 · Taint specification types

The spec types are written now in Go and become YAML-loadable in v0.6, so design them to serialise cleanly.

`engine/taint/spec.go` (sketch)

```go
package taint

type Kind string // "user-input", "sql", "command", "path", "url", "html", "code"

// Source: where untrusted data enters.
type Source struct {
	ID      string   // "express.req.query"
	Match   Matcher  // what IR value or access this applies to
	Kinds   []Kind   // usually ["user-input"]
	Desc    string   // "HTTP query string parameter"
}

// Sink: where tainted data is dangerous.
type Sink struct {
	ID     string   // "node.child_process.exec"
	Match  Matcher  // a call to this qualified name
	Args   []int    // which arguments are dangerous
	Kind   Kind     // "command"
	Rule   string   // rule ID that reports it
}

// Sanitizer: clears specific kinds from a value.
type Sanitizer struct {
	ID     string
	Match  Matcher
	Clears []Kind
	On     SanitizeOn // ReturnValue (default) or Argument(i) for in-place validators
}

// Propagator: how taint moves through a known call when the default isn't right.
type Propagator struct {
	ID    string
	Match Matcher
	From  []Slot // Arg(0), Receiver, …
	To    []Slot // Return, Receiver, Arg(1)…
}

// Matcher selects IR values by tsbridge qualified name and access shape.
type Matcher struct {
	QualifiedName string   // "express:Request.query", "node:child_process.exec"
	Access        Access   // Call, PropertyRead, Parameter, Decorator
	ReceiverType  string   // optional type constraint
}
```

- [x] Implement the types plus a `Spec` registry holding all sources, sinks, sanitizers and propagators, indexed by qualified name for fast lookup.
- [x] Matchers resolve through `tsbridge.QualifiedName` from v0.2, so `const { exec } = require('child_process')` and `import cp from 'node:child_process'` both match.
- [x] Validation: every sink names an existing rule; every kind is known.
- [x] Commit: `feat(engine): taint specification types`.

## Step 3 · Intraprocedural taint propagation

The transfer function decides, for each IR op, how taint labels move from inputs to outputs.

| Op | Propagation in v0.4 |
| --- | --- |
| `const` | Never tainted |
| `assign`, `phi` | Union of inputs |
| `binop` | `+` (string concatenation): union of operands. Comparisons, `in`, `instanceof`: result untainted (booleans can't carry injection) |
| `unop` | `typeof`, `!`, `void`: untainted. `-`, `+`, `~`: untainted (numbers can't inject into string sinks) |
| `template` | Union of expression parts; the static parts are kept for sink checks (Step 5) |
| `load v.prop` / `load v[k]` | Taint of the object (field-insensitive in v0.4); a tainted dynamic key also taints the result *(changed in triage: a key no longer taints the result; ADR 0010)* |
| `store` | The object becomes tainted with the stored value's labels (weak update) |
| `object`, `array` | Union of all elements and spreads |
| `call` to a **source** | Result gets the source's labels |
| `call` to a **sanitizer** | Result = argument taint minus the cleared kinds |
| `call` to a **propagator** | As specified |
| `call` to anything else | Default: result = union of receiver and arguments (string methods like `trim`, `toLowerCase`, `slice`, `split`, `join`, `replace` fall here) |
| `new` | Same default as `call` |
| `await` | Result = taint of the awaited value |
| `closure` | Untainted value; captured cells carry their own taint |
| `catchval` | Untainted (conservative choice; revisit if misses appear) |
| `unknown` | Union of all operands |

**Type-based pruning (big precision win)**

- [x] If a value's TypeScript type is `number`, `boolean`, `bigint` or a union of only those, drop `sql`, `command`, `path` and `url` reachability for it: `parseInt(req.query.id)` can't inject into SQL. Keep the label for traces but mark it numeric.
- [x] Same for values produced by `Number()`, `parseInt`, `parseFloat`, `Boolean()`.

**Engine**

- [x] `engine/taint/intra.go`: runs the sparse solver from Step 1 with this transfer function per function; returns tainted values and, for each, the predecessor values it came from (for traces).
- [x] Every `sink` call is checked after the fixed point: if a dangerous argument carries `user-input` with no sanitizer clearing the sink's kind, emit a candidate finding.
- [x] Unit tests per row of the table, on small TypeScript snippets.
- [x] Commit: `feat(engine): intraprocedural taint propagation`.

## Step 5 · First three rules

Each rule is a small Go file that owns its sinks, its message and its metadata; the taint engine does the hard work.

| Rule ID | Name | CWE | Default severity | Sink kind |
| --- | --- | --- | --- | --- |
| `ts/cmdi` | Command injection | CWE-78 | Critical | command |
| `ts/path-traversal` | Path traversal | CWE-22 | High | path |
| `ts/sqli` | SQL injection | CWE-89 | Critical | sql |

**Each rule must provide**

- [x] Metadata: ID, name, CWE, severity, short description, long description (Markdown), fix guidance with a safe code example.
- [x] A message template filled from the trace: "User input from `req.query.id` (line 12) reaches `pool.query` (line 15) without parameterisation."
- [x] Rule-specific refinements:
  - `ts/sqli`: only report when the dangerous argument is built by concatenation or template with tainted parts; a tainted value passed in the `values` array is safe.
  - `ts/cmdi`: `spawn`/`execFile` with an argument array and no `shell: true` is safe for the args; only the command itself matters.
  - `ts/path-traversal`: suppress when the tainted part only reaches the path after `path.basename`; known false positive when the code checks `startsWith(baseDir)` after `path.resolve` (fixed with path-sensitivity later; document it).
- [x] 10+ positive and 10+ negative fixtures per rule (Step 8).
- [x] `engine/rules/registry.go`: rules self-register; `patchd scan --rules ts/sqli,ts/cmdi` selects a subset; `patchd rules list` prints them.
- [x] Commit: `feat(engine): command injection, path traversal and SQL injection rules`.

## Step 6 · Findings, traces and fingerprints

The finding record designed here is the one the whole product uses later (PR comments, web app, trust layer), so get its shape right now.

`engine/finding.go` (sketch)

```go
type Finding struct {
	RuleID      string
	Severity    Severity
	CWE         []string
	Message     string
	Location    Location       // the sink call
	Trace       []TraceStep    // source → … → sink
	Fingerprint string         // stable identity across commits
	Confidence  Confidence     // engine-level: High, Medium (v0.4 always High or Medium)
	Tags        []string       // "intraprocedural", "numeric-pruned"…
}

type TraceStep struct {
	Location Location         // file, start/end line and column
	Kind     StepKind         // Source, Propagate, Sanitizer, Sink
	Note     string           // "read query parameter id", "concatenated into SQL string"
	Snippet  string           // the source line, trimmed
}
```

**Traces**

- [x] Build the trace by walking back from the sink argument through the predecessor links recorded in Step 3, choosing the shortest path to a source.
- [x] Collapse steps that add nothing (plain copies, phis) so a typical trace is 3–6 readable steps.
- [x] Each step gets a short generated note from its op ("read `req.query.id`", "inserted into template literal", "passed as argument 1 to `pool.query`").

**Fingerprints**

- [x] Hash of: rule ID, file path, enclosing function's qualified name, normalised sink call text, normalised source access text. **Not** line numbers, so unrelated edits don't change the identity.
- [x] Collision handling: append an occurrence index when two findings in one function share a fingerprint.
- [x] Test: moving code down 20 lines or reformatting keeps every fingerprint; renaming the enclosing function changes it.

**Deduplication**

- [x] Several sources reaching one sink produce one finding with the most direct trace plus a count of other sources.
- [x] Commit: `feat(engine): findings, traces and fingerprints`.

## Step 8 · Fixture harness

Fixtures are tiny, self-contained TypeScript files that state their expected findings in comments; they're the engine's main test suite from now on.

**Annotation format**

```ts
import express from "express";
import { exec } from "node:child_process";

const app = express();

app.get("/ping", (req, res) => {
  const host = req.query.host as string;
  exec(`ping -c 1 ${host}`); // expect: ts/cmdi from=7
  res.send("ok");
});

app.get("/safe", (req, res) => {
  const count = Number(req.query.n);
  exec(`echo ${count}`); // expect-none
  res.send("ok");
});
```

- [x] `expect: <rule> [from=<line>]` on the sink line: a finding of that rule must exist there (and its source must be on `from` when given).
- [x] `expect-none` on a line: no finding may be reported there.
- [x] Any finding on a line without an annotation fails the test (catches surprise false positives).
- [x] Fixture folders: `engine/testdata/fixtures/<rule>/positive/*.ts` and `negative/*.ts`, plus a shared `package.json` and `tsconfig.json` with `@types/express`, `@types/node`, `@types/pg` installed once via pnpm into `engine/testdata/fixtures/node_modules` (git-ignored, installed by `pnpm fixtures:install`).
- [x] `engine/fixtures_test.go` discovers all fixtures, runs the full scan pipeline on each folder, and reports mismatches with the trace.
- [x] Coverage goal for v0.4: 30+ positive and 30+ negative per rule, including: template literals, concatenation, `+=` building strings, values passing through local variables, `if`/`else` branches, loops, `try`/`catch`, async/await, destructuring (`const { id } = req.query`), and type-pruned numeric cases.
- [x] `pnpm test` includes the fixture suite.
- [x] Commit: `test(engine): fixture harness and initial fixtures`.

## Step 10 · Precision and false-positive triage

Patchd's promise is that it only reports what's real, so precision is managed from the very first rule.

- [x] Run `patchd scan` on all 10 reference repos (real, non-vulnerable-by-design code) and on Patchd's own `web/` and `ide/` TypeScript.
- [x] Triage every finding into a spreadsheet or `eval/triage/v0.4.yaml`: **true positive**, **false positive** (with cause), or **unclear**.
- [x] Common false-positive causes to look for: field-insensitivity (one tainted property taints the whole object), unrecognised validation (`if (!/^[a-z]+$/.test(x)) return`), allowlist checks, constants mixed with input, admin-only code paths.
- [x] For each cause, decide: fix now (cheap, e.g. a missing sanitizer), defer to a version (record which), or accept with a note in the rule docs.
- [x] Add every false positive you fix as a `negative` fixture so it never comes back.
- [x] **Precision target for v0.4:** ≥ 80% true positives on the reference repos per rule. Below that, the rule ships disabled by default with a flag to enable it. *(`ts/cmdi` and `ts/sqli`: no findings on real code. `ts/path-traversal`: 0 of 3 on real code, so it ships off by default; `--rules ts/path-traversal` turns it on.)*
- [x] Write the known-limitations list into `docs/engine/rules/<rule>.md`.
- [x] Commit: `fix(engine): false positives from v0.4 triage` (as many as needed).
