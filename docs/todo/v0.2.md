`engine/ir/ir.go` (sketch)

```go
package ir

type Module struct {
	File    tsbridge.FileID
	Init    *Func             // top-level statements
	Funcs   []*Func           // every function in the file, including nested
	Exports map[string]ValueID
	Imports []Import
}

type Func struct {
	ID        FuncID
	Name      string           // "handler", "UserService.find", "<anon@12:5>"
	Kind      FuncKind         // Declaration, Arrow, Method, Getter, Setter, Constructor, ClassInit, ModuleInit
	Flags     FuncFlags        // Async, Generator, Static
	Params    []ValueID
	This      ValueID          // NoValue for arrows (they capture this)
	FreeVars  []FreeVar        // captured variables from enclosing functions
	Parent    FuncID           // enclosing function, or NoFunc
	Blocks    []*Block
	Entry     BlockID
	Source    tsbridge.Range
	Syntax    tsbridge.NodeID
}

type Block struct {
	ID       BlockID
	Instrs   []InstrID
	Preds    []BlockID
	Succs    []BlockID         // normal successors
	Handler  BlockID           // exceptional successor (catch/finally), or NoBlock
	Comment  string            // "if.then", "for.body", "catch"… for readable printing
}

type Instr struct {
	ID     InstrID
	Op     Op
	Result ValueID           // NoValue if the instruction produces nothing
	Args   []ValueID
	Aux    Aux               // op-specific: property name, operator, callee hint, literal
	Source tsbridge.Range
	Syntax tsbridge.NodeID
}

type Value struct {
	ID    ValueID
	Kind  ValueKind          // Param, This, Instr, Const, Global, FreeVar, Undefined
	Type  tsbridge.TypeID
	Def   InstrID            // defining instruction for Kind=Instr
	Name  string             // source variable name if any, for printing and traces
}
```

## Step 2 · Instruction set

Keep the set small; every extra op is one more case for every future analysis. Write each op's semantics into `docs/engine/ir-ops.md` as you implement it.

| Op | Form (printed) | Meaning | Can throw |
| --- | --- | --- | --- |
| `const` | `v1 = const "abc"` | Literal: string, number, bigint, boolean, null, undefined, regex | No |
| `assign` | `v2 = v1` | Copy (mostly removed by SSA; kept where it aids traces) | No |
| `binop` | `v3 = binop + v1 v2` | Arithmetic, comparison, bitwise, `in`, `instanceof` (`Aux` holds the operator) | Yes |
| `unop` | `v4 = unop typeof v1` | `!`, `-`, `+`, `~`, `typeof`, `void` | No |
| `template` | `v5 = template ["SELECT ", v1, " FROM t"]` | Template literal with parts kept separate (vital for injection rules) | Yes |
| `load` | `v6 = load v1.name` / `load v1[v2]` | Property or element read (static name in `Aux`, or dynamic key) | Yes |
| `store` | `store v1.name = v2` | Property or element write | Yes |
| `delete` | `delete v1.name` | `delete` operator | Yes |
| `call` | `v7 = call v1(v2, v3) this=v4` | Function or method call; `Aux` holds the syntactic callee and optional-call flag | Yes |
| `new` | `v8 = new v1(v2)` | Constructor call | Yes |
| `object` | `v9 = object {a: v1, ...v2}` | Object literal (keys, computed keys, spreads) | Yes |
| `array` | `v10 = array [v1, ...v2]` | Array literal | Yes |
| `closure` | `v11 = closure f3 [v1, v2]` | Creates a function value capturing free variables | No |
| `spread` | `v12 = spread v1` | Iterates a value for spread contexts | Yes |
| `await` | `v13 = await v1` | Suspends until a promise settles | Yes |
| `yield` | `v14 = yield v1` / `yield* v1` | Generator yield | Yes |
| `phi` | `v15 = phi [b1: v1, b2: v2]` | SSA merge | No |
| `jump` | `jump b3` | Unconditional terminator | No |
| `branch` | `branch v1 b2 b3` | Conditional terminator | No |
| `return` | `return v1` | Terminator | No |
| `throw` | `throw v1` | Terminator; edge to handler | Yes |
| `catchval` | `v16 = catchval` | The caught exception at the start of a handler block | No |
| `unreachable` | `unreachable` | Terminator after code that can't continue | No |
| `unknown` | `v17 = unknown <SyntaxKind>` | Not yet lowered; analyses treat it as "anything" | Yes |

## Step 5 · Expressions

Expressions produce values; anything with short-circuit behaviour becomes control flow so dataflow sees both paths.

- [x] Literals: string, number, bigint, boolean, `null`, regex (pattern kept in `Aux` for ReDoS rules), `undefined` identifier.
- [x] Identifiers: local (SSA value), captured (free-variable load), module-level (global load), unresolved globals (`window`, `process`) as named globals.
- [x] Unary and binary operators, including `in`, `instanceof`, `**`, comma operator.
- [x] **Short-circuit operators** `&&`, `||`, `??` lowered to `branch` + `phi`, not `binop`.
- [x] Conditional `a ? b : c` lowered to `branch` + `phi`.
- [x] **Optional chaining** `a?.b`, `a?.[k]`, `a?.()`: branch on nullish with `undefined` on the short-circuit path, for the whole chain.
- [x] Assignment `=`, compound (`+=`, `??=`, `||=`, `&&=` with their short-circuit semantics), to identifiers, properties and elements.
- [x] Increment and decrement, prefix and postfix.
- [x] Property and element access: static name in `Aux`, dynamic key as an argument; private fields `#x` with a distinct name prefix.
- [x] Calls: plain, method (`this` = receiver), `super.method()`, optional call, spread arguments, `call`/`apply`/`bind` kept as ordinary calls (resolved in v0.5).
- [x] `new`, `new.target`, `import.meta`.
- [x] **Template literals** into `template` with each static part and each expression kept separate; **tagged templates** into a `call` of the tag with the strings array and values (`Drizzle's sql tag, Prisma.sql`).
- [x] Parenthesised expressions, `as`, `satisfies`, non-null `!`, type assertions `<T>x`: no runtime effect, so lower to the inner value but keep the node for traces.
- [x] `typeof`, `void`, `delete`.
- [x] JSX: elements and fragments lowered to `call` of a synthetic `jsx(tag, props, children)` with props as an `object`; keep `dangerouslySetInnerHTML` as an ordinary prop (rules match on it later).
- [x] Commit: `feat(engine): lower expressions`. — *Done: in `b7415fd`.*

## Step 6 · Functions and closures

- [x] `arguments` object as a synthetic value for non-arrow functions that use it.

## Step 10 · SSA construction and verification

SSA (every local variable assigned exactly once, with `phi` at merge points) makes dataflow simple and fast; build it during lowering, then verify it independently.

**Construction (Braun et al. 2013)**

- [x] Track the current definition of each local variable per block (`writeVariable` / `readVariable`).
- [x] Reading in a block with one predecessor: recurse to it. With several: create an operand-less `phi`, record it, then fill operands from each predecessor.
- [x] Blocks are **sealed** once all predecessors are known (after loop back-edges are added); reads in unsealed blocks create incomplete phis completed at sealing.
- [x] Remove trivial phis (all operands the same value or the phi itself), recursively.
- [x] Exceptional edges count as predecessors of handler blocks, so variables modified inside `try` merge correctly into `catch` and `finally`.
- [x] Captured variables (cells, Step 6) are excluded from SSA: they stay `load`/`store`.

**Dominator tree**

- [x] `engine/ir/dom.go`: Cooper–Harvey–Kennedy iterative dominator algorithm; dominator tree and dominance frontiers available to later passes.

**Verifier (`ir.Validate`)**

- [x] Every block has exactly one terminator, at the end.
- [x] Preds and succs are consistent in both directions; the entry block has no preds.
- [x] Every value is defined before use along every path (definition dominates use; phi operands checked against the matching predecessor).
- [x] Each phi has exactly one operand per predecessor.
- [x] No instruction refers to a value from another function except through `FreeVars`.
- [x] Every instruction has a source range inside its function's range.
- [x] Verifier runs in every IR test and, behind a flag, on every function of the reference repos in CI. — *Done: `--verify` in the `ir-coverage` workflow.*
- [x] Commit: `feat(engine): SSA construction, dominators and IR verifier`. — *Done: in `b7415fd`, dominator and verifier fixes in `220743e`.*

## Step 12 · Performance and memory

The IR for a large repo is millions of instructions, so compact representation matters now, before analyses depend on it.

- [x] Arena allocation per function: values, instructions and blocks in slices indexed by ID; no per-instruction heap objects.
- [x] Small argument lists stored inline (most instructions have ≤ 3 args). — *Done differently: every instruction's arguments are a range of one per-function slice, so no instruction allocates and none has a size limit.*
- [x] Interned strings for property names and identifiers per program. — *Done: `ir.Name` (Go's `unique`) with a per-file cache; value names are interned so the IR does not keep sources alive.*
- [x] Lower files in parallel (one goroutine per file, bounded by the worker pool from v0.2); modules are independent at this stage. — *Done: `BuildProgram` runs one goroutine per CPU over the files; `LoadAll`'s pool bounds the projects.*
